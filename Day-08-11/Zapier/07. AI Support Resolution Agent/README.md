# Task 7 — AI Customer Support Resolution Agent

## 📋 Task Description

Autonomous Zapier Agent that reasons over customer messages, decides which tool to use, and either resolves the issue or escalates — without a fixed scripted path.

- **Data layer:**
  1. Subscribed Customer Table (Customer ID, Name, Email, Plan, Subscription Status)
  2. Ticket Table (Ticket ID, Customer, Issue, Category, Priority, Action, Status) — Ticket ID is a sequential identifier (`TKT-0001`, `TKT-0002`, …) generated by a dedicated second Zap, not by the agent
- **Agent tools:** Search Tickets, Create Ticket, Update Ticket, Send Email — customer lookup handled via a Knowledge Source instead of a discrete Search Customer tool call (see design note below)
- **Agent reasoning:** determine intent → decide what data is needed → pick the right tool → decide answer vs. escalate
- **Action routing:** password problem → reset instructions; billing question → look up customer/order data; duplicate payment → finance ticket; technical issue → technical support ticket; angry/urgent → escalate to human
- **Duplicate prevention:** agent must Search Tickets first — only Create Ticket if no open ticket exists for the same customer+issue, otherwise Update Ticket

## ⚙️ How It Works

Two automations working together: the **Zapier Agent** itself (one autonomous unit, not a multi-step Zap chain) for reasoning/resolution, plus a small companion **Zap** that assigns sequential Ticket IDs behind the scenes.

**Agent — reasoning and resolution:**

1. **Trigger — Gmail: New Email.** Every inbound message to the support mailbox starts the agent.
2. **STEP 0 — reasoning stated first.** Before taking any action, the agent must output its reasoning in a fixed format:`INTENT: <Password/Login | Billing question | Duplicate payment | Technical issue | Angry/Urgent>`,`DATA NEEDED: <what and why>`, `TOOL: <which tool and why>`.
3. This forces the model to commit to an intent classification and a plan before calling anything — decisions are auditable in the run log, not just implicit in tool calls.
4. **Customer lookup via Knowledge Source.** Rather than a callable "Search Customer" tool, the `Subscribed Customers` table (Customer ID, Name, Email, Plan, Subscription Status) is attached directly as the agent's **Knowledge Source**, synced from Zapier Tables. The agent retrieves customer context by reasoning over this synced data instead of issuing a separate find-record call.
5. **STEP 3 — duplicate prevention (mandatory search-before-create).** Before ever creating a ticket, the agent must call **Zapier Tables: Find Records** on the Tickets table with **exactly two fixed filters**: Lookup Field 1 = Customer (the customer key), Lookup Field 2 = Status ("Open"), both `exact` match. This step is never skipped, even if the message looks brand-new.
   - **No match** → proceed to create a new ticket.
   - **Match found** → the existing open ticket is **updated** (e.g., escalated), never duplicated. Verified live in Test 3 below.
6. **STEP 5 — ticket fields on create.** When creating, **Zapier Tables: Create Record** on the Tickets table sets Status = `Open` (or `Escalated` for Angry/Urgent), Customer = the exact key returned by the lookup (never retyped by the model), plus Category (must match the table's dropdown exactly: `Finance | Technical | Billing | Account`), Priority (`Low < Medium < High < Urgent`), and Action (a short description of what was done). The agent does **not** set Ticket ID itself — that's the companion Zap's job (next).
7. **Resolution / notification — Gmail: Send Email.** Every path ends with a personalized email from `anila.toor@gmail.com` ("Support Team", MATalogics Internship mailbox): password issues get direct reset instructions with **no ticket created**; billing/duplicate/technical issues get a confirmation referencing the ticket ID and next steps; angry/urgent messages get an apology + escalation confirmation.

**Companion Zap — Sequential Ticket ID Auto-Generator** (fires right after the agent creates a ticket row):

1. **Zapier Tables: New Record** — triggers on the Tickets table whenever the agent's Create Record step lands a new row.
2. **Storage by Zapier: Increment Value** — bumps a persistent counter by 1 on every run, independent of the table itself, so the count survives even if table rows are later deleted.
3. **Code by Zapier: Run Javascript** — formats the incremented number into the `TKT-0001` style zero-padded ID string.
4. **Zapier Tables: Update Record** — writes the formatted ID back into the `Ticket ID` field of the record that just triggered the Zap.

This keeps ID generation decoupled from the agent (which never has to reason about counters), at the cost of a small race: the Ticket ID appears on the record a moment after creation, not atomically with it. Because the Storage counter persists independently of table rows, deleting stray test tickets doesn't roll the counter back — the evidence screenshot's clean `TKT-0001`/`TKT-0002` sequence required manually resetting the counter/IDs after cleanup, rather than deletions alone re-triggering a gapless sequence.

## 🔧 Configuration

- **Trigger:** Gmail: New Email.
- **Priority scale (used throughout):** `Low < Medium < High < Urgent` — "higher priority" means further right on this scale.
- **Category values (must match the Tickets table dropdown exactly):** `Finance`, `Technical`, `Billing`, `Account`.
- **Reasoning-first rule (STEP 0):** the agent must state INTENT / DATA NEEDED / TOOL before calling any tool — makes the decision path inspectable per run.
- **Tools this agent can use:**
  - `Zapier Tables: Find Records` — Table: Tickets, Operator: `exact` on both filters, Filter Count: 2 (Customer, Status).
  - `Zapier Tables: Create Record` — Table: Tickets, default Status: `Open`.
  - `Zapier Tables: Update Record` — Table: Tickets.
  - `Gmail: Send Email` — From: `anila.toor@gmail.com`, From Name: `"Support Team"`, mailbox label: MATalogics Internship.
  - Default tools (Visit Site & Web Search) left enabled but unused in the tested scenarios.
- **Knowledge source:** `Zapier Tables: 'Subscribed Customers'` — kept in sync with the Customers table; the agent looks up plan/status from this instead of a dedicated Search Customer tool call.
- **Ticket ID generator (separate Zap):** New Record (Tickets table) → Storage by Zapier: Increment Value → Code by Zapier (Javascript, zero-pads to `TKT-0001` format) → Update Record — writes the formatted ID back onto the ticket that triggered it. Runs independently of the agent. *Note: Storage by Zapier's counter persists across table edits, so deleting stray test tickets doesn't roll it back on its own — the clean sequence in the evidence screenshot required manually resetting the counter/IDs after cleanup.*
- **Duplicate-prevention rule (hard constraint in the instructions):** Search Tickets is never skipped, filters are fixed (Customer = customer key, Status = "Open"), and the agent is explicitly told never to set Lookup Field 2 to Customer and never to ask the user to confirm filter values — it sets them and runs.
- **Escalation criteria:** explicit rule, not free-form sentiment — an `Angry/Urgent` intent classification (STEP 0) escalates the ticket: Status → `Escalated`, Priority → `Urgent`, and the customer is told a senior team member will follow up directly.

## 🧪 Test Input & Output

All four scenarios run against the same test customer (`CUST-001`, Anila Toor, Pro plan) to prove the duplicate-prevention and escalation logic against one continuously-evolving ticket — all emails below are **real, delivered Gmail messages**, not just Agent Preview text.

| Scenario                                  | Input                                                  | Output                                                                                                                                                                                                                                                                                        |
| ----------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Duplicate charge (first report)           | "I was charged twice for my subscription."             | Search Tickets found no open match → new ticket created:`CUST-001`, Category = Finance, Priority = High, Status = Open, Action = "Duplicate charge reported"; real email received: *"We've Received Your Duplicate Charge Report – Ticket #CUST-001"*                                   |
| Password/login issue                      | Password reset request                                 | **No ticket created** (per workflow rule for Password/Login issues); real email received: *"Password Reset Instructions – Regain Access to Your Account"* with step-by-step reset link, 5-minute delivery note, and 24-hour expiry                                                   |
| Same duplicate-charge issue re-submitted  | Customer follows up again on the same duplicate charge | Search Tickets matched the existing**open Finance ticket** for `CUST-001` → agent **updates** it instead of creating a duplicate; Agent Preview reports Goal Status: COMPLETE, "ticket has already been processed... no further action required"                               |
| Angry/urgent follow-up on the same ticket | Customer message expressing frustration at the delay   | Existing ticket**escalated**, not duplicated: Priority upgraded `High → Urgent`, Status `Open → Escalated`, Action = "URGENT ESCALATION: ..."; real email received: *"URGENT: Your Case Has Been Escalated – Senior Team Taking Over Now"*, committing to contact within hours |
